<a id="two-packages"></a>

## 两个包

两半拆分，是为了让绘制代码永远不会了解 agent：

| 包 | 职责 |
| --- | --- |
| [`@dshline/renderer`](../packages/renderer) | 字符宽度、键盘解码、输入行、边框盒与屏幕。不导入 Harness 的任何内容，因此可以在没有终端和模型的情况下测试。 |
| [`@dshline/dshline`](../packages/dshline) | 插件本身：会话循环、把会话事件转换为会话记录行、Harness 集成点，以及视图注册表。 |

这条边界有双重价值。渲染器自身没有任何依赖，这正是本插件不会给用户的环境增加任何东西的原因。而且由于它对 agent 一无所知，本页关于宽度、截断和转义的每一条规则都可以直接测试。

<a id="it-prints-and-updates-one-small-area"></a>

## 只打印并更新一小块区域

聊天会话记录只会增长，因此渲染器不保存整个屏幕的副本。完成后的输出打印到终端自己的滚动历史中，之后不再触碰。只有底部区域——仍在到来的回复、提问、输入行——会被原位重绘。

正因如此，滚动位置从来不需要这段代码跟踪，窗口调整大小时也不需要重新布局任何东西。

一条规则保证正确性：活动区域必须始终是屏幕上最后的内容，因此每一次写入都经由 `Screen`。

这也是本界面从不切换到备用屏幕的原因。滚动、用鼠标选择文本和复制的行为与任何其他命令完全一致，而不是在界面内部重建。

<a id="future-views-still-become-bounded-terminal-rows"></a>

## 未来的视图仍然归结为有界的终端行

dshline 刻意不会用拥有历史终端输出的协调器（reconciler）替换 `Screen`，也不会采用备用屏幕/全屏会话记录模型。React + Ink 可以做不同的终端取舍；本项目保留其「追加 + 活动区域」模型，因为终端自身的滚动缓冲区（scrollback）是产品的一部分。

未来的视图抽象可以是声明式的，但它必须归结为供 `TuiSlots` 与 `Screen` 使用的有界行列表。它不能持有内存中的会话记录、重写已提交的行，或绕过 `Screen` 绘制自己的区域。

<a id="a-reply-is-printed-as-it-arrives"></a>

## 回复随到随打印

每一行完成时，只要它的换行符一到，就打印进滚动历史。只有最后那行未完成的行留在活动区域。

能放进活动区域的未完成行，与已提交的会话记录使用同一个行内格式化器、基于同一份块状态绘制——因此 `**bold**` 闭合片段在其标记到达的瞬间就应用样式，围栏内的一行部分内容按代码渲染，而提交这一行不会改变它的形态。被截断的后缀保持字面形式：它既没有源行的开头，也没有更早的分隔符上下文，对任何一边的猜测都会隐藏文本。活动区域就是已提交路径早一个换行符的版本，而不是同一文本的第二次渲染。

这有两个好处。重绘成本保持恒定，而不是随回复长度增长。并且比窗口更长的回复会像普通终端一样滚动，而不是被修剪到能容纳的大小。

当完整消息在回复末尾到达时，它只贡献流式输出尚未能显示的部分。这正是回复不会被打印两次的原因。

<a id="reasoning-is-shown-while-it-happens"></a>

## 推理过程在发生时就显示

会推理的模型把思考作为另一种输出发送，有时占据大半轮。默认情况下，它以暗色、安静的方式打印在回答上方，让屏幕显示模型在工作，而不是在空白处转圈。`/thinking` 只改变这个终端中的显示投影：隐藏时仍会正常接收并协调推理内容，再次显示时只显示此后到达的推理。已经提交到滚动历史的内容不会重写；重放时按当前窗口偏好处理已存储的推理，同时仍显示完整回答。

<a id="suggestions-come-from-what-the-agent-really-has"></a>

## 建议来自 agent 真正拥有的东西

输入 `/` 列出这个 agent 实际注册的命令。输入 `@` 列出文件夹中的真实条目。`tab` 接受高亮的建议；当它补全当前 token 时 `enter` 也接受，否则正常提交。`ctrl-enter` 以完全相同的方式裁定，因为那个修饰键选择的是一次提交如何投递，而不该改变提交的内容——若不纳入，它会越过列表并发送打了一半的 token。方向键移动，`esc` 关闭。

建议列表刻意不是模态框。模态框会吞掉每一次按键，而建议必须与输入共存——因此列表只认领自己的按键，并且随输入收窄，而不是困住输入行。精确的命令、路径或参数已然完整，所以 `enter` 仍然属于输入行，并保留命令原本的裸行为。

只考虑光标前的文本。针对光标后的文本补全会重写没人要求改动的字符。而且 `/` 只在行首开始命令，因为 `/help` 是命令，而 `see /etc/hosts` 是路径。

被接受的建议与粘贴文本一样被安全化。文件名可以包含文件系统允许的任何字符，而输入行的内容绘制时不会第二次转义。

<a id="tool-output-is-drawn-the-way-the-tool-asks"></a>

## 工具输出按工具要求的方式绘制

每个工具通过两个 Harness 文档说明为可随时安全调用的函数，描述其调用与结果应如何呈现。

于是 shell 命令成为带边框的框，以它运行的文件夹为标题，退出码位于输出框上。文件变更成为红绿相间的 diff。搜索把匹配结果按文件分组。文件读取保留文件自身的行号。没有描述任何内容的工具也能正确显示，因为每种呈现类型都文档化会回退为原始文本——而且从不为某个特定工具的名字添加特例。

改变文件的工具从两个函数返回它们的 diff，因为在大多数界面里，完成的卡片会替换待定的卡片。而在本界面输出从不重绘，diff 在结束时打印一次。这也是两者中更真实的一个：它展示的是实际发生的，而不是被提议的。

`ctrl-o` 在循环切换之前有一个首要职责：省略了输出的卡片已经把这些行提交进滚动缓冲区，任何细节级别都无法找回它们（级别只影响从今往后绘制的卡片）。因此当最近一张已完成的工具卡片被截断时，`ctrl-o` 打开检视器——一个活动区域浮层，重新渲染那张卡片的呈现、滚到被省略的行，然后消失而不触碰已提交的会话记录。在其中，`↑`/`↓` 滚动一张卡片，`←`/`→` 在保留的卡片之间切换；`ctrl-o` 仍可用作移到较旧卡片的快捷键。这在 `full` 与 `compact` 细节级别下都适用，因为检视器有自己的、大得多的行预算：卡片的行被永久提交，因此上限在几百行；检视器的行是开窗滚动的，可以到几千行。否则 `ctrl-o` 循环切换每张卡片显示多少内容：`compact`、`full`、`hidden`。即使 `hidden` 也仍会显示调用发生过，并仍会显示非零退出码，因为隐藏了这些的会话记录会歪曲实际运行了什么。

哪一「端」的正文能活过预算，是按呈现类型分别决定的，而不是一劳永逸。文件读取、搜索和 diff 保留前面的行，因为那是被请求的内容。命令保留最后的行：运行 `pnpm test` 想知道的失败与总结在底部，而锚定头部会留下横幅、丢掉答案。它的省略标记位于框的起始处而不是结尾，因此它待在自己所说的那些行之上。

<a id="the-status-line-drops-details-instead-of-cutting-them"></a>

## 状态行丢弃细节而不是截断它们

上下文用量显示为数字旁边的条形——`██████░░ 6.2k/8.0k`——但只在至少一个条形块会被填充时显示。DeepSeek 的上下文窗口容纳一百万 token，所以对任何现实中的会话，按比例的条形都是空的，而永远为空的条形占用空间却不传达任何信息。非按比例的条形会更快填满，但会歪曲窗口有多满。填充部分向下取整，因为看起来 94% 就满了的条形夸大了它存在的唯一意义。

随着终端变窄，整条提示被丢弃而不是被切成两半——读作 `ctrl-d qui` 的提示看起来像缺陷，而不是帮助。模型名在上下文数字之前被丢弃，因为模型在会话期间不变，而数字会变。

会话的 token 与成本总计位于两者之间，在模型名之后、上下文读数之前被放弃。两半都遵循同一个论证：总计是对会话已花费的核算，而读数决定会话是否还能工作，两者之中读数是你离不开的那个。推理级别作为模型名的一部分绘制，而不是在它旁边，并且随模型名一起消失——留在被丢弃的模型之后的级别，读起来会像属于接下来出现的东西。

模型名在某些界面中被钉在右边缘，那读起来不错，但这里并非如此：右边缘是按键提示的位置，随宽度出现和消失的提示比一列对齐更有价值。

在决定上述任何一项之前，会先为一个提示留出空间，因此更丰富的读数永远不会成为最后一条提示消失的原因。没有它，加入会话总计就足以让八十列终端——大多数终端打开时的宽度——显示所有数字而毫无帮助。取而代之被放弃的是条形，它是旁边数字的图示；而提示是这个界面唯一说明如何离开它的地方。

<a id="prices-are-shipped-and-every-one-of-them-is-wrong-eventually"></a>

## 价格随包发布，而它们最终都会被证明是错的

token 由提供方计数，并从会话日志读出，因此 `↑` 与 `↓` 就是你被计费的内容。它们在与绘制会话记录相同的投影中汇总，这就是为什么恢复会话会带回它的总计：重放让同样的事件经过同一个计数器，没有第二条会脱节于第一条的恢复路径。

价格不能那样工作，因为没有一条已发布的价格永远成立，而烤进发布版的表格会一直报告它构建时用的数字。答案不是不发布任何价格——一个连两个模型的任何价格都给不出的界面是更差的取舍——而是把它们发布在改一个条目只需两行编辑的地方，并精确说明它们覆盖什么。

价格按 **提供方路由** 关联，绝不仅仅按模型 id。同一个经网关到达的模型由网关计费，因此裸模型默认值会把一家公司的价目表安到另一家的账单上。命名了三条路由——DeepSeek 自己的，以及已安装目录携带的两条 OpenCode 路由，`opencode` 对应 OpenCode Zen、`opencode-go` 对应 OpenCode Go——它们共用一组只写一次的数字，这是对 OpenCode 这一对的刻意近似：转售商的发票是自己的单据。命名路由正是让这个近似保持可见、并局限于我们为其制作的这三条的方法。无人定价的路由显示 token 而旁边没有金额，这正是上下文条形已经遵循的规则：在没有什么真实可画之前，什么都不画。只有部分计价的会话会被标记，因为悄悄缺了一半流量的总计读起来与完整的完全一样。仅按模型 id 关联条目仍然可能，而且需要你明确要求。

关于美元数字到底是什么，说一句。在按量付费路由上，`$` 估算花费的钱；在 OpenCode Go 上，同样的数字是按订阅额度计数的、以美元计量的用量，而不是单独一张账单。UI 无法从日志区分——它报告该路由定价所用的核算方式——因此本文档把它说清楚，而不是让某一个读数看起来普遍成立。

一个数字之下有两样变化，二者都是按消息结算，而不是按总计。**哪个模型**——会话中途换模型在这里是一条命令，因此按它恰好结束时的模型给整个对话定价，两个方向都是错的。以及**何时**——DeepSeek 在早晨的两个时间段内收费大约翻倍，因此按某人重新打开它的时刻定价，会把一夜的工作按早晨的价格计费。每个事件都带有自己的时间戳，这正是让诚实的版本不比错误的版本更难的原因。时间窗口按 UTC 读取，因为提供方以这个时区发布时间表；按本地时间读取会把每个人的价格按各自的时区偏移移动。

<a id="a-command-that-takes-a-value-offers-its-values"></a>

## 接受值的命令会提供其取值

这里有三个命令会更改设置，每一个都直接接受值——`/reasoning max`、`/model deepseek-v4-pro`、`/usage tokens`——或在不带参数输入时打开选择器。选择器是阅读四条描述的好方式，却是设置你已知之物的坏方式，把它作为唯一入口会在用户与一个单词之间隔一层浮层。

因此建议列表也携带取值。命令名后一旦出现空格，它接受的取值就出现在光标下，接受一个取值与接受命令名是同样的手势。由于列表在接受的候选项上会重新打开，补全 `/rea` 无需第二次按键就能把级别放上屏幕——选择器退化为当你想要描述而不是大家都走的路径时的后备。

取值从何而来是值得小心的部分。它们是向运行者询问的，而不是在这里列出的，因为它们是活的：存在哪些推理级别取决于当前选中的路由，而关闭了思考的部署只宣传一个。只有本界面自己的命令提供取值。向 Harness 注册的命令把它的参数描述为自由文本提示，而不是集合，因此无可枚举——而为某个命令编造候选项会宣传一个其处理器从未同意的词汇。

参数只在它是单个单词时补全。`/tmp is full` 是关于文件夹的一句话，在这样一行中途打开列表，就是抢走用户正当作普通句子写下的这一行。

<a id="the-profiler-stays-live-without-inventing-history"></a>

## 性能分析器保持实时，而不编造历史

`/timing` 绘制一轮会话的时间正在去向何处，而不只是它去过哪里。启用期间，一个小的缩进面板会在整轮以及其后的空闲时间里留在活动区域中。它是朴素的而非带框的，因为它是紧挨着 composer 与状态行的常驻装饰，而不是一张索要焦点的模态卡片。它被限制在六行，被省略的跨度在最后一行里计数，因此一轮调用几十个工具也无法把重绘区域撑到超出终端。这个上限也正是它的常驻得以诚实的原因：composer 为它预留了一个标题行的预算，而在容不下两者的终端上，仪表让位于交互——先是正文行，然后是标题，绝不是输入行。

面板就是全部呈现。在回复下面再提交一份完成后的图表会重复同一个事实，并把可选的仪表变成永久的会话记录噪声，因此一次完成的测量留在原地，直到下一轮取代它。计时关闭时，这个 slot 完全不贡献任何行。

有意思的决策是它的条形以什么为基准。

显而易见的选择是这一轮：每一行都是整体的一个分数，加起来等于一。它也是错的。一个步骤内的工具调用彼此同时运行，思考跨步骤与它们交错，因此这些是重叠的跨度——一个十秒的回合里两个十秒的工具各自都正确。以总计为基准，它们会是半满的条形，暗示另外发生了二十秒的事；彼此为基准，它们说出的才是实际发生的，即两者都花了十秒。

所以条形以最长行为基准，而回合的挂钟时间打印在标题里，在那里它不对下面的行做任何声明。图表支持的是「其中哪一个花了时间」——这正是任何人打出这条命令要问的问题。它刻意不支持的是「这一轮有多少时间在思考」，因为日志回答不了这个问题。

每一行画成暗色轨道之上的一道半高笔画，而不是空白之上的整块方块。有两种误读必须同时防住。空白的余量掩盖了一行的刻度到哪里结束，于是一条不满的条形浮在它的行内；而相邻行上的整高方块，在邻近跨度量得相近的地方会融成一整块板，藏起一个跨度的条形在哪里停下、下一个从哪里开始。无论长度如何，笔画都在行与行之间留出空白，而轨道标出每一行刻度的末端。这是刻意偏离状态行的方块条：那个仪表是独立的一条，而这些行是叠起来的。

被省略的那一行报告它所隐藏的最长跨度，标注为 `max`，绝不是它们的和。这些跨度彼此重叠，因此求和得到的是做过的工作量而不是流逝的时间——它可以超过标题里打印的那一轮本身，而一个与它上方时钟相矛盾的数字读起来会像面板坏了，而不像一层抽象。

面板已经活着时才到达的跨度，会在接下来的几次工作心跳里把它的条形缓入，而不是闪到全宽——后者正是纯测量会画出的样子，因为第一个跨度总是最长的。缓入计的是那些心跳，绝不是时间，也绝不是原始重绘：流式分块会在一次心跳之内把面板重绘许多次，而那些渲染刷新测量，却不消耗这个效果。它随工作转子本就驱动的心跳推进，不添加自己的计时器，并且完全活在视图内部，从第一帧起，不断增长的条形旁边显示的就是真实的测量值。面板没有可装饰的到达事件的任何东西——一次在轮中途打开的偏好、一轮被保留的已完成会话——都立即以全宽绘制，因为装饰绝不能重放历史。

它由实时事件流驱动，而不是共享投影，这不是与用量计数器的对称，而是刻意与之相反。恢复的会话在重放日志时会滤掉流式分块——它们是日志同时整份存储的回复的逐 token 形态，两者都重放会把每条消息打印两次。位于该过滤器之后的性能分析器会把每一轮过去的会话画得像模型根本没有思考过，因此重新打开的附着改为显示一个诚实的 `no turn measured yet` 占位。

已完成的跨度使用那些事件的时间戳，此后绝不改变。进行中的一轮和进行中的工具还没有结束事件，因此它们的临时时长按工作转子已经在驱动的挂钟走动；reasoning 与 output 随它们流式时间戳的到达而推进。一旦某个结果或轮次结束落地，它的日志时间戳就取代那个临时的时钟读数。把这个例外讲明白，比在事件之间冻结进行中的工作，或假装渲染器时钟本就是已保存日志的一部分，都更真实。

<a id="character-widths-follow-the-unicode-standard"></a>

## 字符宽度遵循 Unicode 标准

Harness 不止被一种语言使用，其内置的 agent 预设以中文命名。一个占两列却被量成一的字符会推挤后面每一行，而不只是它自己的——因此宽度遵循 Unicode 东亚宽度属性，重绘算术计数的是「绘制出的」行，这样换行行或东亚文本行也能被正确计数。

<a id="measuring-and-cutting-agree-about-escape-sequences"></a>

## 测量与截断对转义序列保持一致

`displayWidth` 忽略转义序列，因此换行与截断也必须忽略它们。两者都把文本拆成零宽转义序列与可见字符，绝不在序列中间截断，并在续行上重新打开任何活动的颜色。着色行的测量宽于其绘制宽度会过早换行，并连累每一行带边框的行。

截断也关闭它打开的东西。丢弃被缩短行末尾的复位码会让它的颜色保持开启，下一个绘制的东西会继承它——暗色的推理行渗进下方的输入行。

<a id="untrusted-text-is-made-safe-before-it-is-drawn"></a>

## 不受信任的文本在绘制前先被安全化

终端把某些字节序列当作命令而不是文本。因此任何由模型、工具或会话日志产生的东西都不受信任：工具输出中的转义序列可以重绘活动区域，回车可以把光标移走。

所有这类文本先被转换为可见形式，控制字符以脱字符记法（caret notation）显示。添加颜色是单独一步，只应用于本项目自己组合的文本。

未经安全化就到达终端的路径在这里是安全缺陷，而不是外观问题。

<a id="colour-is-chosen-by-role-not-by-name"></a>

## 颜色按角色选择，而不是按名字

要求红色的调用点做出了一个谁也无法重新审视的决定。`style(text, 'red')` 对失败的工具和 diff 中被删除的行写法完全相同，因此第二套配色永远无法只移动其中一个而不移动另一个——而四个互不相关的含义，警告、加载动画、上下文压力以及每一个浮层边框，也以同样的方式共用黄色。真正的原因是这个，而不是缺少一个主题选择器，所以过去始终只有一套配色。

因此调用点命名的是**角色**——这段文本是什么——而配色说明它看起来如何。只有后者才是主题可以选择的。今天恰好共用一种颜色的两个角色，只要含义不同就保持分开，因为配色总是可以给两个角色相同的值，而一旦调用点忘记了自己指的是哪一个，就没有任何东西能把一个角色重新拆开。`muted` 与 `subdued` 被分开正是这个理由的具体版本：一个是绝对的灰色，另一个是与当前已生效前景色叠加的属性，因此为浅色终端编写的配色必须移动前者而保留后者。

每一种外观都是一串 SGR 参数，这正是让配色能以 24 位色编写而无需改动任何绘制代码的原因。对宽度计算而言，整个转义序列本来就是一个零宽度记号，无论它带有多少参数。每个角色还声明自己的十六色形式，因此基本终端显示的内容是有人做出的决定，而不是没人看过的最近似颜色。

结束符始终是完整的重置。仅重置前景色的形式渲染结果完全相同，却会被每一次换行当作开启序列读取——被重放到每一个续行上，并且永远不会清除它已经累积的内容，也就是上面描述的颜色渗入输入框的问题。

配色是进程级全局的，理由和原始模式一样：终端只有一个。安装一套配色会返回把上一套放回去的清理函数，而重复调用该函数是安全的。

**每一层拥有自己的角色。**渲染器只声明它自己绘制的那些——Markdown 结构与通用强调——不多不少，因为它不能知道什么是回复、工具调用或上下文压力；正是这条规则让它保持无依赖。前端从自己的包中扩充渲染器的角色词汇来添加自己的角色，因此仍然只有一个 `paint` 和一套配色，而配色的完整性会跨这两半一起检查。

终端能显示多少颜色由 Node 回答，而不是本项目自行维护的策略。`getColorDepth` 已经处理 `NO_COLOR`、`FORCE_COLOR`、`COLORTERM` 与 `TERM`，还有手写规则表会遗漏的 CI 变量与 Windows 版本号。自己拥有这套策略意味着要维护它，并且会在无声中出错；委托出去只需要一次映射：把 Node 表示单色的 `1` 映射到"什么都不输出"的那个深度。

<a id="markdown-is-rendered-and-made-safe-while-it-is-parsed"></a>

## Markdown 被渲染，并在解析时安全化

回复带有标题、强调、行内与围栏代码、列表、引用、分隔线与链接。支持的是一组刻意很小的子集，手写在 `packages/renderer/src/markdown.ts` 中，因为使用解析库会破坏无依赖这一属性。

强调遵循 CommonMark 关于哪些字符可以打开和关闭它的规则，有一个刻意的区别。后跟空格的标记不能打开，前有空格则不能关闭，因此 `2 * 3 * 4` 保持为算术。下划线不能接触单词，因此 `snake_case_name` 与 `file_name.ts` 保持原样。区别在于 `__init__` 按原样保留，而不是被读作粗体：在关于代码的回复里，那是 Python 名字的概率远高于强调，而破坏读者可能需要输入的变量名，代价大于失去格式。`__bold text__` 与 `_italic_` 仍然都有效。

操作的顺序就是安全规则：每一段文本都在添加颜色**之前**被安全化，绝不会在之后。使文本安全的函数也会中和转义字符本身，因此对已着色的输出运行它会破坏颜色——而只对部分片段运行会让控制序列从其他任何地方漏过。模型可以把一个放到普通散文、标题、链接目标或代码围栏里，四处都被覆盖。

<a id="pasted-text-is-untrusted-too"></a>

## 粘贴文本同样不受信任

人们粘贴日志，这使粘贴成为整个界面中最可能的终端控制字符来源。

粘贴文本在插入时被清理，而不是在它之后被测量或绘制的每个位置：行尾变成 `\n`，制表符变成空格，任何剩余的控制字符变成脱字符记法。

制表符到处都被展开，而不仅仅是在这里。制表符是把终端移动到下一个制表位的单个字符，留下一个会让每一个宽度计算都与屏幕不一致——带边框的行被填充到错误的宽度，右边框移动。在缓冲区中保持一种表示，意味着每一个宽度、光标与绘制计算读到的都是终端实际接收的文本。

终端可以标记粘贴的开始与结束，这正是多行粘贴成为一条消息、而不是一阵 `enter` 按键的原因。分片到达的粘贴会被持有到其结束标记到来，无论花多久：慢粘贴与被放弃的粘贴看起来一模一样，而把真实的粘贴截短会把文档的其余部分作为独立消息发送。

<a id="keyboard-input-is-read-in-both-formats"></a>

## 键盘输入以两种格式读取

区分 `shift-enter` 与 `enter` 需要终端的配合，因此启动时渲染器会请求 kitty 键盘协议的最低选项，*转义码消歧（disambiguate escape codes）*。

这个请求不是附加性的。支持它的终端会完全停止为 `esc`、`alt` 与 **`ctrl`** 组合发送旧字节值：`ctrl-c` 变成 `CSI 99 ; 5 u`，再也不是 `0x03`。

因此两种格式都被解码，而新格式的表是从旧格式的表**派生**的，而不是写在旁边。`ctrl` 快捷键的新码是它的旧字节值加 `0x60`，所以给一张表加一个快捷键，两张表都有。只以旧字节值为人所知的快捷键在新模式有效的那些终端上会彻底失效——那不是一个优雅的回退，而是回归。

`enter`、`tab` 与 `backspace` 是协议自身的例外，未修改时保留它们的旧值。同一信息的更老 xterm 格式也被读取，因为终端选择哪种格式不是用户的问题。界面退出时该模式被关闭，因此下一个程序按它期望的方式读取输入。

孤立的 `esc` 字节在读到的内容末尾会被持有，而不是立即判定，因为它是解码器识别的每一个序列的第一个字节，包括粘贴标记。短暂的停顿解决它：一旦终端停止发送，那个字节就是 Escape 键。

<a id="queue-and-steer-are-the-readers-choice-not-the-agents-status"></a>

## 排队与导向是读者的选择，而不是 agent 状态的产物

Harness 一直有两个目的地来接收你输入的东西。`followup` 把它放进 agent 的 `next-turn` 列表，在下一个轮次边界成为独立的一轮。`steer` 把它放进 `next-step`，已经在运行的那一轮会在最近的步骤边界取用它并继续步进。

本界面过去是靠偶然在两者之间选择的。`enter` 调用的是 agent 状态恰好允许的那一个——运行中用 `steer`，否则用 `followup`——因此每一次繁忙期提交都会加入已经在进行的推理，而且永远无法请求一个后续轮次。这是把一个真实差异当成实现细节呈现：“然后更新 changelog”和“别再用那个文件了”并不是同一条指令，其中只有一条属于你眼前那一轮。

所以它成为一个偏好，其默认值是**排队**。两个理由，按顺序。所采纳的 Harness 世代自己的 Web 客户端把 `queue` 作为繁忙期 `enter` 的默认值，而同一个 agent 的两个界面对同一个键的含义各说各话，对读者来说比其中任一选择都更糟。而且排队是错了代价更小的那一个：本该导向却成了后续，只是晚一轮抵达；本该后续却成了导向，则已经被并入一轮正在推理别的事情的过程，无法收回。

只有*一轮正在运行时*的 `enter` 受影响。空闲时没有步骤供导向抵达——Harness 本身也会把空闲期的导向化解为一次被唤醒的提示轮次——所以在那里造出一个区分，属于本界面自己的发明，而不是 Harness 的。

`ctrl-enter` 为单条消息以另一种方式发送。它是这里唯一被刻意从不宣传的键，原因与本界面推荐 `alt-enter` 作为换行键的原因相同：未处于增强键盘模式的终端为 `ctrl-enter` 与 `enter` 发送完全相同的字节，而且没有任何查询能在需要绘制提示之前把它们区分开。宣传它的输入框，等于是在告诉大多数读者去按一个会悄悄做出相反行为的键。在终端无法发出它的地方，这次按下就是 `enter`——即读者自己的偏好，而绝不是第三种行为——而 `/enter` 与使用指南负责教这个手势。

本界面**不**拥有的东西是那个队列。Harness 持有这些列表、它们的顺序、持久性与认领；这里的选择只是一条输入用两个既有动词中的哪一个来投递，且只调用一次。状态行实时读取那些列表，而不是统计提交过什么，因为在这里维护的计数会在任何别的东西移动收件箱的那一刻失准——步骤边界上的一次认领、一次取消、某个插件自己的插入——而且恢复时还得从它并不拥有的事件里重建。

有一个后果值得写下来，因为它是一个选择而不是疏漏。`ctrl-c` 会连同这一轮一起丢弃待处理输入，因为 Harness 的取消在没有被要求保留时会清空两个列表。保留是 Web 客户端的做法，在那里也是对的：取消是一个按钮，旁边就是读者随后可以编辑的可见队列。而在终端里，`ctrl-c` 意味着停止——而存活下来的排队工作会在被中止的那一轮收敛到空闲的那一刻自行把 agent 再次启动，那就不是中断了。所以待处理的提示会消失，而那条说明这一轮被中断的行会说明有多少条随之消失。它们仍然只差一个 `↑`：一条已提交的行无论 agent 对它做了什么，都在窗口的输入历史里。

<a id="the-empty-composer-answers-three-questions-in-one-row"></a>

## 空的输入框用一行回答三个问题

一个空的输入行应当说明你可以在其中输入、`enter` 此刻会做什么，以及去哪里找到其余一切。它应当安静地把这些都说出来，而且不能占掉一行。

```text
› ask anything · / menu      idle
› type to queue              a turn is running, and enter queues
› type to steer              a turn is running, and enter steers
```

这个提示只是呈现，别无其他：它在绘制时由 agent 的状态产生并直接交给框架，因此从不进入缓冲区、历史、撤销栈、一次提交，或补全据以计算的文本。绘制它的分支正是以缓冲区为空为条件的那一个，这使上述属性是结构性的，而不是一句承诺。

它写 `/ menu` 而不是 `/ commands`，因为那个界面不只有命令：它承载本界面自己的命令、agent 已注册的命令，以及用户可直接调用的技能——而技能不是命令。

片段整段丢弃，按一个顺序，与状态行丢弃它自己的片段完全一样：`› ask anything · / me` 读起来像渲染故障，而不像帮助。提示符本身从不被丢弃，因为它是真正的可输入信号，而光标在每一个宽度下都落在它之后。

曾经出错的那一部分更微妙。这段文本过去是用会换行的适配助手来适配宽度的，而它会按需要返回任意多行——因此在十九列以下，空的输入框已经会画出第五行，而空分支是活动区里唯一不花自己行预算的视图。在较短的终端上，这会把活动区推出屏幕，那里已经滚出去的行再也无法被抵达或擦除，而这正是“追加加活动区”模型唯一无法承受的事。更长的提示会把那个悬崖推进普通的分屏宽度里。所以这个阶梯在构造上就返回单独一行，并且在每一个宽度、两种状态下都只把恰好一行交给框架。

<a id="image-paths-become-durable-references-only-at-send"></a>

## 图片路径只在发送时成为持久引用

图片草稿最初只是当前会话 attachment 拥有的路径。暂存不做 I/O：读者可以列出、移除或清空草稿，
而切换会话不会让草稿泄漏到另一个 Agent。只有提交时才通过 `ctx.fs` 解析并读取每个路径，使用部署的
字节上限，然后通过 `ctx.attachments` 发布完整批次。发布成功会得到不透明、内容寻址的
`ImageBlock` 引用；dshline 从不自造 id，也不在日志中保存 base64、图片字节或主机路径。

这次准入是一个可取消的用户操作，尽管持久发布本身是原子的且没有取消信号。从第一次读取直到命令
派发，`ctrl-c` 都拥有该操作；取消或会话拆卸后才完成的结果不能进入旧 Agent 的收件箱。失败会保留
提示与草稿，因而重试不会静默地把多模态请求变成纯文本请求。

`@path` 仍是文本，因为源码文件和目录是供模型工具使用的引用，不是图片字节。`/image` 刻意保持显式；
已注册命令只有在 Harness 描述符声明 `input.attachments` 时才收到草稿。模型名称绝不充当视觉能力白名单：
明确的纯文本模态会在 I/O 前拒绝，而缺失的元数据仍代表未知，并交由 Harness 判断。

<a id="commands-report-what-they-did"></a>

## 命令报告它们做了什么

命令不产生模型回复，因此它对自身的说明是唯一证明发生过什么的证据。命令行被回显，其结果作为一条备注打印——失败时带 `✗`，因为静默失败的命令看起来与坏掉完全一样。

两者都来自 Harness 自己对命令开始与结束的记录，而不是你按下 enter 的时刻。这对恢复会话很重要：这两条记录保存在日志里，因此恢复的会话显示命令的方式与实时会话完全一致。直接打印到屏幕会让每条命令结果在恢复时消失。

命令也可能完全无文本地成功。那是有效的结果，而返回它的命令正是本界面无法以其他方式显示其效果的命令——因此不会略过它，而是按名称确认这条命令。Harness 还允许结果指向另一个以更丰富方式呈现相同信息的事件。这个提示在这里被刻意忽略，因为本界面不显示那些事件，遵从它会让命令不可见。

被拒绝为未知命令的行不同：什么也没有运行，因此 Harness 不记录任何东西，消息只来自本界面。它不是已保存对话的一部分，会话重新打开时也不会再次出现。

`/exit`、`/quit`、`/model`、`/reasoning`、`/usage`、`/timing`、`/new` 与 `/clear` 由本界面回答，而不是向 Harness 注册。`/clear` 是 `/new` 加上一项呈现意图：其全新会话的切换只在新会话真正创建成功后才清空可见显示区域——失败或被恢复的切换绝不清空——并且使用与 `ctrl-l` 相同的显示清空路径，不会显式清除终端的回滚缓存。Harness 的命令注册表被进程中的每个界面共享，而网页或自动化服务器没有可退出的终端、可打开的选择器、可切换读数的状态行。它们仍然出现在 `/` 列表中、与其他命令在一起，因为打出 `/` 的人想看自己能打什么，而不是它来自哪个注册表。

看起来像命令但未命名任何东西的行会被报告为未知，使用 Harness 自己对命令行是什么的规则，因此两者不会不一致。

<a id="what-a-turn-will-do-outranks-what-it-costs"></a>

## 一轮会话将要做什么，优先于它要花多少钱

计划模式与运行中的目标是这里仅有的两个改变 agent「做什么」而非「说什么」的状态，而会话记录会隐藏两者。设置它们的命令打印过一行，早已滚动走；之后的一切看起来像普通会话，而 agent 安静地拒绝编辑文件，或安静地自行再取一轮。这正是状态行存在的理由，所以两者都在其中。

它们用不同的方式读取，每一种都是其所有者文档化的方式，这个差异不是不一致。计划模式从日志中折叠出来，因为控制器直说它不保留实时镜像，界面通过事件流观察已提交的切换——这有一个好结果：恢复的会话从重放中恢复该状态，与会话总计的方式相同。目标则是向它的服务询问，因为日志回答不了那个关键问题。持久记录说目标是活动的；**本进程**是否有权再取一轮是进程局部的，且刻意永不持久化，因此持有活动目标的恢复会话并不是即将运行它的会话。只读日志会在每一次恢复时报告一场不会发生的运行。

这个区别正是读数有三种形态而不是两种的原因。会继续的目标是轮数对战上限的计数，颜色与工作中的旋转指示器相同，因为它就是那个东西。已设置但无处可去的目标直说。暂停、受阻或完成的目标显示其阶段而不是计数，因为已停止目标的轮数是历史，而不是进展。

两者都是在终端变窄时最后被放弃的东西——在模型名、总计、条形、上下文读数与按键提示之后。上面描述的提示预留是在**每一级内部**花费的，而不是跨所有级别，这用一句话概括了整个顺序：帮助比更丰富的读数重要，而不如知道会话即将自行行动重要。而且模式是整块丢弃、绝不缩短，原因与本页其他每个片段相同：`goal 12/25` 不是比 `goal 12/256` 更小的真相，而是不同的一个。

<a id="the-model-you-pick-is-one-setting-not-one-sessions"></a>

## 你选的模型是一个设置，而不是某次会话的

切换模型是两个容易误认为一个的独立动作。第一个写入一个可变引用，agent 在每个步骤进入提示组装时读取它；这正是切换生效的方式，它完全在内存中。第二个把选择存入 Harness 的设置文档，这是 Web 界面 Models 页读写的那一节。

只做第一个是站得住脚的，而且曾持续过一段时间：终端是尝试东西的地方，而悄悄为其他每个界面更改设置的实验会是一个意外。让天平倒向另一边的，是读取早已不对称。本界面一直在启动时**读取**那一节，因此在 Web 界面选择的模型会在下次启动时到达这里——而在这里选择的不去任何地方。单向同步的设置比双向同步的更难以推理，因为没有一条用户可以持有的规则：它取决于你上次在哪里碰过它。

所以它双向同步，而命令在发生时的那一行就说出来，而不是留待发现。顺序是有规则的部分：引用先写、无条件写，存储允许失败。即将运行的这一轮已经被许诺了一个模型，而写不进的设置文档是说明的理由，而不是这一轮悄悄用旧模型的理由。

选择整体存储，路由与推理级别一起，即使只有其中一个改变了。那一节只放一个选择；只写一半会让某个级别适用于下一次会话恰好打开的模型。

<a id="the-interface-is-made-of-plugins-too"></a>

## 界面本身也是由插件组成的

横幅、输入行、状态行和每一个边框盒都是 `ctx.tuiSlots` 中独立的注册项——终端版的 Web 界面视图注册表。位置有名字（`stream`、`composer`、`completion`、`timing`、`status`），因此内部视图通过命名一个位置来选择它出现在哪里，而拥有文本输入的视图报告光标属于哪里。

```ts
ctx.tuiSlots.register('status', { render: () => ['my widget'] })
ctx.tuiSlots.pushOverlay(myPrompt)   // takes the whole area and every keystroke
```

这是当前内部组合模型的图示，而不是第三方集成配方：`TuiSlots` 与 `TuiOverlay` 是 1.0 之前实验性的词汇，不是稳定的公共 SDK。边框盒堆叠，只有最上面一个绘制并接收按键，因此在审批等待时提出的问题不会混进它。`ctrl-d` 在边框盒收到按键之前被处理，因为退出在任何地方都意味着同一件事。

<a id="sharing-a-frame-is-not-sharing-a-state-machine"></a>

## 共享边框，而不是共享状态机

composer 是界面唯一的固定锚点，而临时浏览器——Work、Sessions、Plugins、工具检视器、选择器——是同一个锚点展开后的样子。两者都通过同一个共享边框绘制：左边框的标签永远是 `dshline`，右边的标签说明屏幕上是什么（输入时是工作区，浏览器打开时是视图身份），而浏览器的导航帮助位于下边框内部，而不是悬在分离盒子下方的一行里。

这种共享刻意只是呈现层面上的。挂载的浮层仍然像从前一样替换整个活动区域并接管每一次按键——它下面没有 composer，可搜索选择器打出的查询仍然属于选择器本身，关闭浮层时 composer 原样恢复。显而易见的替代方案——让浮层真的从 composer 里长出来——会合并两个绝不能合并的东西：composer 持有缓冲区与光标，浮层持有一个临时交互；把它们耦合起来，就是浏览器开始吞掉为输入行敲下的字的方式。因此视觉连续性只用一个共享绘制辅助函数换来，除此之外什么都不共享：无状态、无按键、无生命周期、不持有对 Harness 的视图。

边框本身是渲染器的一个原语，对 agent 一无所知：上边框两端的标签、下边框里的帮助、以及分隔行。两个标签相撞时右边先让位——`dshline` 锚点正是整个安排的意义所在；帮助整段丢弃，绝不丢出半个指令，因此窄终端上读到的是 `esc`，永远不会是 `esc clo`。因为帮助行移进了边框，浏览器比从前「盒子加下方帮助行」少占一行活动区；每个浏览器的行预算都是从其真实几何重新推导出来的，而不是把测试调到恰好通过为止。

<a id="sessions-and-resuming"></a>

## 会话与恢复

当前激活的配置文件提供 Harness 会话持久化时，`--resume` 从已持久化的日志重建会话记录，并通过与实时绘制**相同**的代码重绘它，因此重新打开的会话看起来与你当初看着发生的那个一模一样。两条各自独立的绘制路径在其中任何一条第一次变动时就会分道扬镳。没有持久化的配置文件仍然可以运行全新会话；dshline 不另加一个存储。

被重放的是实际说过的记录，而不是模型当前看到的版本。两者不同：当历史被总结以节省上下文时，模型的视图隐藏了被替换的消息。重放那个视图会抹掉你已经读过的对话片段。它们已从模型的记忆中消失，但它们确实发生过。

恢复的会话保留它创建时的文件夹。该文件夹记录在会话文件中并被视为权威，因此恢复时 `-C` 被忽略，而不是悄悄把旧对话搬到新地方。

从运行中的窗口内重新打开——`/sessions`——用同样的方式绘制，而这是它必须满足的约束：你终端里已有的会话记录是已提交的滚动缓冲区，因此新恢复的会话是**追加在它下面**，而不是替换它。已打印的内容绝不重写，这就是为什么一个窗口可以不借助备用屏幕在会话间移动。改变的是谁拥有活动区域：窗口保留终端与键盘，而被附着的会话的视图、日志监听器与能力适配器会被拆除，并围绕新 agent 重建。

浏览器的 2.0 能力保持在同一条权威线上。语料库过滤、血统导航、会话内搜索与游标分页都是 `ctx.sessionQuery` 的投影——工作区与年龄用 `filterSessions` 子句、祖先用 `traceSession`、单个会话的命中用 `searchEvents`、两个分页作用域用不透明游标——而重命名是唯一的变更，委派给 `ctx.sessionTitle`，作用于本窗口正在驱动的会话，其仅记日志的 `session/title` 事件携带显式的 `user` 来源。浏览器各用一次按键打开小的子浮层（过滤选择器、血统、事件搜索、重命名提示）；每个子浮层拥有自己的选择、查询与视口，关闭它恢复父层的精确状态，因为两者从不共享活动区域状态。用哪一个按键，跟随问题的作用域：`ctrl-f` 用于过滤，因为它们收窄语料库；`→` 用于披露单个会话的界面——它的事实，以及只对它有意义的操作。这个拆分也正是让浏览保持廉价的原因：事件计数与最后活动时间背后那次有界的日志读取发生在那个界面被打开时，因此移动光标唯一花费的就是一份标题与年龄的清单。

分页把 Harness 的游标当作纯粹的请求状态：它只对产生它的那个规范化请求有效，因此编辑查询或改变过滤会重新开始链，一页已加载的结果恰好追加一次，而在游标之下变动的语料库表现为显式刷新，而不是静默拼接。来源分类出于必要只是呈现层的——Harness 不发布来源谓词——并对 Harness 返回的权威观测头部应用：搜索页的批量标题观测解析出同一会话的偏好活动头部，恢复后端自己的命中投影可能省略的 `origin`，这就是为什么计数器可以说"返回中命中数"，而不是假装后端按来源排序。
