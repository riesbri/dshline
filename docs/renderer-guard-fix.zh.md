[English](renderer-guard-fix.md) | 中文

这是[守卫审查发现1](renderer-guard-review.zh.md)的修复，实现在草稿
[PR #302](https://github.com/riesbri/dshline/pull/302) 的
守卫提交 `4ba66c1` 和纯分配叶子修复提交 `79948df`。
修的是守卫成本，而非准入策略：**TS 仍为默认；五个排除、旧阈值、边界、Unicode
检查、回退和编译策略全部不变。** Rust 仍仅是显式选择后才可准入的纯叶子。
未合并、发布或安装到工作 profile。

## 改了什么，以及为什么决定不会改变

- ASCII 成员判断使用**不带 `u`** 的 `/[^\x00-\x7f]/`。`search` 仍返回首个非 ASCII
  UTF-16 偏移；`test` 仍判断是否存在非 ASCII 码元。不可能有“所有码元都为 ASCII
  而码点非 ASCII”的情况；代理对与孤立代理码元在两种模式下都包含非 ASCII 码元。
- 原有显式高/低代理码元检查仍恰好消耗第一个码点。在其结束位置及之后发现的
  非 ASCII 后缀边缘码元必然属于另一个码点，因此 width 可立即返回 undefined，
  与原先后缀测试结论相同，不会把第一个代理对计两次。
- 全 ASCII 谓词在首/末码元非 ASCII 时立即拒绝；空串仍视为 ASCII。
  否则执行相同的成员测试。
- 长 width 末尾两个码元为 ASCII 时的旧捷径保留。分派选择、`AUTO_MIN_UNITS`、
  窄列规则、2048码元/±256列边界、默认值、Unicode 版本协商、准入后错误处理与
  Rust 宽度/扫描策略都没改。额外的 chunk 分配修复在下文说明。

四个缺陷输入现在**后缀切片零次，正则测试零次**；只有两个 width 调用做搜索，
均在偏移1找到首个 CJK。Width 最多读取四个单独码元，tail/chunk 读取两个。
一般 ASCII 分类仍可能需要不可避免的线性扫描，但实际分派输入最多2048码元，
扫描已不使用 Unicode 模式。这不是声称所有字符串分类都为 O(1)。

## 决定等价性与故障检测

冻结 oracle 来自 `25a2501`。审计工具重新编译该不可变的真实源码树，检查其中的
守卫函数与冻结测试 oracle 一致；编译后的旧版身份也匹配原审查保留的身份。

**每台机器16,796,982次决定完全一致，零不匹配：**

- 全部1,114,112个码点/代理码元值，含全部有效补充平面代理对和2048个孤立代理码元，
  三种上下文、五种操作：**16,711,680**次比较。
- **677**个位置化 UTF-16/ANSI/控制字符串 ×14列预算 ×9操作：**85,302**次比较。
  长度0/1/2/3/63/64/65/511/512/513/2047/2048/2049；预算
  −257/−256/−1/0/1/31/32/33/63/64/65/255/256/257。原始谓词测试也包含分派准入
  范围外的值，证明那些决定同样不变。

三台机器各自先通过未修改的历史路由测试，然后**逐个删除五个守卫，每次都失败**，
失败原因是禁止的原生变换被调用：共15个被拒绝的守卫变异，不是一次性全删。
Linux 上的新增测试还拒绝恢复 Unicode 正则模式、破坏代理对长度、删掉后缀边缘短路这三类错误。
即便丢失捷径后决定仍正确，结构性“不扫后缀”测试也会失败。

公共 API/声明/schema 不变。86个黄金请求/输出及非 reference 元数据不变，
只刷新源码/构建身份元数据。新增冻结测试模块已同时纳入原生输入哈希与构建器
脏输入检查。
新增 Rust 行容量测试还覆盖样式重放、组合字符、孤立代理码元、空行及巨大直接库预算；
删除样式重放会使该具名测试失败。宽度查表与全部13个 Rust 语义测试通过。

## 旧版 / 修复 / 无守卫 / TS 控制计时

下表单位为 µs/调用：十一轮的轮次中位数再取中位数；每轮五个交错批均值，
500次预热，八个变化且扁平化的输入。校准用三个批次的中位数设定≥10ms目标，
调用数上限4194304。每个批次后轮换变体顺序，而不只是整轮之间轮换。
全部26个稀疏/密集/ASCII负载均保留。
这是边界 CPU 计时，不是单调用尾延迟或端到端延迟承诺。

“旧版”是重新编译的**真实25a2501**，不是更早的5e48基线或手写替代参照。
修复与仅基准用的无守卫图共用当前 addon；显式 TS 不通过它做变换。**旧版重新构建真实的
原始25a2501 addon，并带独立干净源码输入证明**。双方使用相同固定编译策略。
无守卫仅去掉性能回退守卫函数，保留边界/最小长度/版本检查。
四个缺陷输入全部继续准入：旧版/修复/无守卫每八输入调用原生八次，显式 TS 零次。
Width2048/512 为 `'a中' + 'a'.repeat(n - 3) + '中'`；tail/chunk 为
`'a'.repeat(2047) + '中'`、80列（语料改变首个 ASCII 码元）。

### 既有叶子的纯分配修复

提交79948df按 `min(段落UTF-16长度, 原有夹限列预算)` 预留每个 chunk 行容量，
不再每次断行都从零反复扩容。既有开放样式的长度加到下一行容量提示，并保持同样的
样式复制。零宽文本/样式重放仍可使行增长；直接库的巨大预算不会仅因预算巨大而
预留超出输入的空间。这只改变分配：扫描器、宽度、断行、reset策略、边界、五个守卫
和准入全部不变。

最终实验保留**相同的十一轮交错协议和验收指标**，只加入上述明确的容量修复。
在自有临时分离工作树重新构建原始25a2501 Rust/TS，而非悄悄把新内核放进旧版图。
当前带守卫/无守卫共用当前字节；旧版具有独立验证的原始 addon/证明。
范围扩展及此前两次失败均明确披露。
