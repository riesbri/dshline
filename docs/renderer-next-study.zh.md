# Rust 性能进一步研究

[English](renderer-next-study.md) | 中文

## 结论

**PARTIAL：原型有可测量的潜力，但不是生产变更。** 下一步最值得推进的是紧凑的
Unicode 查找表，以及现有 TypeScript 宿主下范围受限的原生叶子函数集成。ASCII
换行应单独研究，直到连带退化得到解决。终端和 Harness 的所有权保持不变。本次研究既不修改，
也不替代现有渲染器 PR。

## 方法与证据

[可运行的研究代码](../spikes/001-rust-performance/README.md) 从已审查的渲染器源码
`5e48b70` 出发，将 crate 和编译后的模块复制到临时目录。生产包源码、配置、
profile 和依赖均保持不变。测量环境仅为 Rust 1.99.0、Node 24.18.0 和
Linux ARM64/Cortex-A76。本地锁定依赖的离线构建不是托管发布产物，本报告也不将
现有六平台正确性批准扩展到这些原型。

[初步计时](../spikes/001-rust-performance/results/phase1-bench.json) 对五种构建执行
135 项负载和三轮轮换顺序测量。每项负载使用八个变化的输入，并在计时前与 TS
进行精确比较。每轮保留五个经过校准的批次平均值。比值仅代表本地 CPU 测量，
不代表整轮提速或单次调用延迟百分位数。

[精简候选方案复测](../spikes/001-rust-performance/results/bench.json) 同样对 135 项
负载执行三轮测量，比较基线、仅查找表、查找表/ASCII 换行候选方案及独立 TS。
下面是 2048 单元输入的代表性结果，单位为微秒（三轮中位数的中位数）：

| 直接 addon 操作 | 当前 Rust | 仅查找表 | 组合候选方案 |
| --- | ---: | ---: | ---: |
| 宽度 / CJK | 49.08 | 6.78 | 6.78 |
| 宽度 / emoji | 25.62 | 5.27 | 5.28 |
| 尾部 / CJK / 40 列 | 61.45 | 17.60 | 17.80 |
| 填充 / CJK / 40 列 | 51.02 | 7.75 | 7.72 |
| 换行 / ASCII / 40 列 | 89.65 | 90.39 | 46.49 |
| 宽度 / ASCII | 3.15 | 3.21 | 3.95 |
| 填充 / ASCII / 40 列 | 4.37 | 4.50 | 5.24 |

最后两行很重要：精简组合方案仍使部分 ASCII 路径退化 10–25%，且三轮结果一致。
因此其性能**尚未达到生产要求**。本研究未确定这些连带退化的原因；不能将其
解释为噪声，也不能悄悄省略。应先推进仅查找表方案，在组合变更前隔离并解决
组合方案的连带影响。

## 哪些方案保留下来

| 方案 | 发现 | 决策 |
| --- | --- | --- |
| 去重 Unicode 页表 | 两次索引读取替代范围搜索；所有码点均与项目现有宽度一致 | 推进 |
| 可打印 ASCII 源码片段换行 | 换行更快，但精简组合方案使其他 ASCII 操作退化 | 在严格守卫下单独研究 |
| 通用源码片段换行 | 首个原型丢失了跳过空格旁的零宽 token | 拒绝；保留原始 Unicode/ANSI 内核 |
| 两遍扫描的轻分配尾部截取 | 不加查找表时，长 CJK 尾部从约 61 µs 退化到 108 µs；也慢于仅加查找表的版本 | 拒绝 |
| ThinLTO 加单个代码生成单元 | 组合二进制更小，但计时有好有坏，包括换行变慢 | 不作为统一提速策略启用 |
| 原生叶子函数集成 | 无需迁移所有权即可覆盖 TS 所有的 frame/Screen 工作 | 作为独立实现推进 |

查找表包含 4352 个双字节页索引，以及 108 个独特的 256 字节页：表数据共
**36352 字节**。它仅由仓库现有 Unicode 策略推导。这不意味着二进制恰好增加
同样的大小；段布局和对齐也有影响。宽度仍按码点求和，保留孤立代理项单元，
忽略已识别的 ANSI，并保持控制字符的原有宽度。不替换字素策略，不做规范化，
不引入缓存或新依赖。

保留下来的换行原型仅接纳可打印 ASCII 和换行符。其他文本在执行前选择原始的
纯 Rust 内核。被拒绝的通用原型在种子 `2810499053`、预算 `-256` 下失败；
研究保留了该回归探针。减少分配本身不保证提速：被拒绝的尾部方案额外完整扫描
一次，代价超过了省去 token 向量的收益。

## 重要的集成发现

公共后端导出与内部派发并不相同。`screen.ts` 和 `box.ts` 直接导入 `width.ts`；
因此 auto 模式的回调 frame 和普通 Screen 工作绕过原生宽度/换行选择器。
观测到的原始追踪中，公共换行调用一次原生函数，而回调 frame 和 Screen 配方
均为零。更快的内核无法加速根本不使用它的调用点。

临时实验只替换复制模块图中有边界限制的宽度/换行叶子函数。原始 TypeScript
仍负责执行边框回调、拥有 Screen 状态、提交滚动缓冲区，并决定所有写入顺序。
测试精确比较写入数组，包括光标、过期状态重绘、收缩和终端宽度变化。即使使用
现有 addon，合成宿主测量也有明显收益；但它不证明真实会话或 PTY 性能。

[宿主复测](../spikes/001-rust-performance/results/host.json) 包含 18 项合成用例、
三轮轮换顺序测量和精确写入比较。下面是 2048 单元输入的代表性结果，单位为微秒：

| TS 所有的负载 | 当前 auto | 叶子路由，当前 addon | 叶子路由，候选方案 |
| --- | ---: | ---: | ---: |
| 回调 frame / ASCII | 259.66 | 88.57 | 63.26 |
| Screen 配方 / ASCII | 470.36 | 156.82 | 94.97 |
| 回调 frame / CJK | 576.91 | 336.89 | 285.18 |
| Screen 配方 / CJK | 758.37 | 301.69 | 201.20 |
| Screen 配方 / ANSI | 390.05 | 125.59 | 127.33 |

仅改变路由就已改善这些负载。ANSI 一行也说明，候选方案并不总比路由到当前
addon 更快。这些是使用内存写入目标的有界合成 CPU 配方，而非终端 I/O 计时。

[检查](../spikes/001-rust-performance/results/checks.json) 覆盖六种构建：6684672 次
穷举码点比较、1675848 次直接精确变换比较、516 次黄金样例重放、资源限制拒绝，
以及独立且均衡的 ASCII 覆盖。[变异检查](../spikes/001-rust-performance/results/mutations.json)
能拒绝错误的 CJK 宽度，以及移除 ASCII 换行守卫这两种故意引入的错误。

生产实现应引入无循环依赖的基础函数选择 seam，而不是让已被 `backend.ts` 导入
的模块反过来导入它。复用现有的带守卫可选加载器、显式模式、长度/列数限制和
原生输出验证。缺失产物或不支持的输入必须在执行前选择 TS；已获准的原生调用
发生错误时，仍必须直接传播，不能重试 TS。回调/proxy/getter 处理、调色板观测
和流式文档所有权都保持不变。

## 现有替代方案与延后工作

现有 napi-rs 绑定仍足够适用。Node-API 字符串提取会将 UTF-16 复制到调用方缓冲区；
[其约定](https://nodejs.org/api/n-api.html#napi_get_value_string_utf16) 并不支持将任意
JavaScript 字符串存储视为借用的 Rust 切片。不要仅为节省小规模的有界复制而
使用原始 V8 访问，或新增 unsafe 零复制路径。

[unicode-width](https://docs.rs/unicode-width/latest/unicode_width/) 包含字符串/序列
宽度行为，并非本项目的码点求和约定。[memchr](https://docs.rs/memchr/latest/memchr/)
搜索字节切片，也不能直接替换 UTF-16 宽度扫描器。两者均不能替代现有策略。
手写 SIMD 和 PGO 仍是未经验证的后续方向，而非已承诺的收益。可先测量编译器
的可移植向量化，再考虑特定平台的 unsafe 内建函数。

[Cargo profile](https://doc.rust-lang.org/cargo/reference/profiles.html) 允许测量
LTO/代码生成单元的取舍。保留 `panic = "unwind"`：abort 会终止嵌入它的 Harness
进程，而不是让现有 panic 守卫返回错误。不要将 `target-cpu=native` 构建作为
可移植预构建包分发；[rustc](https://doc.rust-lang.org/rustc/codegen-options/index.html#target-cpu)
将该设置定义为构建宿主 CPU。

## 建议的生产实施顺序

1. 实现派生查找表，加入确定性的时效检查、穷举宽度一致性验证和现有六平台原生门禁。
2. 为选定的 TS 宿主加入无循环依赖的原生叶子函数选择器。除精确写入外，还验证真实
   终端模拟器单元格、光标/BCE、回调观测和无操作重绘。在改变推广策略前重复合成与
   PTY 测量。
3. 单独研究带守卫的 ASCII 换行，解决连带退化后再采用；保留专门的 ASCII、畸形输入及
   零宽/跳过空格回归覆盖。
4. 除非新的完整边界测量证明值得选择原生，否则微小调用和窄行数组继续使用 TS。
   在分析确认边界成本仍显著之前，延后批处理/直接复合 ABI；绝不将 Harness/领域对象
   传给 Rust。

本研究不包含合并、发布、真实模型轮次、profile 修改、终端状态迁移、带 sanitizer/
覆盖率插桩的模糊测试或无泄漏认证。已完成自查；未使用独立审查者或 subagent。

复查发现，研究工具中可预测的共享临时路径和目录条目 stat/读取模式触发了
CodeQL 告警。准备步骤现在只创建全新的私有目录；后续工具要求显式传入私有
目录，并检查所有权/权限，不跟随末级符号链接。目录枚举使用返回的条目元数据，
而不另外对路径执行 stat。回归检查拒绝复用、共享和符号链接路径。保留的测量
工具哈希对应路径修复前的 `b07d423`；原始计时不会被标记为新运行或生产证据。
